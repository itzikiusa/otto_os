## Resolved finding and closure evidence

### R2-C1 [major, resolved] Settings edits after the save response could disappear during the following refresh

**Closure:** The save response now records `acknowledgedRevision` without deleting the draft. `app.render()` synchronously captures the outgoing form before clearing its DOM; `settings.render()` clears a saved baseline only when the current revision still equals the acknowledgment. It retains the same draft object and saving flag, and removes the acknowledgment when cleaning. An edit during either follow-up request increments the registered draft's revision, so the subsequent render preserves it. The asynchronous save's `finally` still owns the retained object's saving flag. This directly closes the traced ownership gap without moving it to the overview await.

**Executed evidence inspected, not rerun:** `/tmp/otto-quality-20261007-plugin-review-red.log` records both people-held and overview-held regressions failing before the repair: actual `submitted calibration`, expected `typed after config success`. `/tmp/otto-quality-20261007-plugin-full-final.log` records both passing and the complete plugin suite at **470 passed, 0 failed, 2 skipped, 472 total**. The browser tests hold the respective post-save GET response, type the new value, release the response, perform another refresh, and assert the new value survives. Skipped cases are not passes. Source and test bodies were independently read.

The following trace records the pre-repair defect; line numbers refer to that reviewed version.

**Location:** `examples/plugins/team-performance/ui/views/settings.js:303` (draft deletion at line 304), capture ownership check at line 153, asynchronous refresh at lines 310–311.

**Intended:** Saving acknowledges only the submitted revision. Newer edits stay in an account-owned draft across refreshes, including edits made while any part of the save flow awaits network work. This is stated in the fix plan, source comment, and `SCAN-CONTRACT.md`.

**Actual:** Once PUT `/config` succeeds with no intervening edit, the handler deletes the account's draft from the map, then awaits `app.refreshPeople()`. The form remains mounted and its inputs remain editable. Their input/change handler calls `capture()`, but that function immediately returns because `drafts.get(account) !== draft`. The later metrics refresh rerenders the form from saved server values and loses the new edit.

**Evidence: confirmed, hand-traced reachable event sequence.**

1. On Settings, change working hours from 8 to 7 and click Save. `submittedRevision` matches the draft's current revision.
2. Let the people write and PUT `/config` succeed. No newer edit has happened yet, so lines 303–304 remove the draft. Hold the subsequent GET `/people` response pending.
3. In the still-mounted form, type working hours 6. The input is enabled (only the Save button was disabled). The capture handler at line 153 sees no registered draft and returns without recording 6.
4. Release GET `/people`, then the overview/settings refresh requests. `app.refresh()` calls the view renderer, which calls `settings.capture()`; the same ownership mismatch still refuses capture. A new draft is constructed because the map entry is absent. The refreshed form displays the persisted 7; unsaved 6 has disappeared.

**Fix direction:** Retain a registered, clean draft while the mounted form can still accept edits and while post-save refreshes are pending. Retire/replace it only at an ownership-safe render boundary after another capture, or track a saved revision separately from draft lifetime. Do not fix this by disabling only the Save button. Preserve the existing stale-account checks and failed-save behavior.

**Regression:** Extend `examples/plugins/team-performance/test/browser.e2e.test.js`. Hold the *post-save GET `/people`* after PUT `/config` has resolved; type a newer setting, release the held response, and assert the newer value survives the resulting rerender and account round trip. The existing “edits during Save” test delaying PUT `/config` does not exercise this later window. Also exercise an account switch during this window so a deferred old-account response cannot retire the new account's draft.

The coordinator was notified immediately; the subsequent red/green evidence above confirms the original trace and focused repair.

## Integration follow-up: two WebSocket revocation races

**Status: resolved; no open confirmed findings in this reviewed scope.** These were real production auth-lifecycle defects exposed by the integration gate and its neighboring-branch trace, not timeout-only test repairs. The existing 2,500 ms socket-close budgets were not increased. `docs/contracts/ws.md:412–417` promises a short revocation recheck and close code 4401; the source also explicitly promises to retry transient store failures on the next tick.

### R2-C2 [major, resolved] Handshake-time revocation became the socket's baseline

The original `/ws/events` path authenticated the token before upgrading, but `handle_events` read `revocation_generation()` only after upgrade setup and initial timer awaits. A logout between those points could evict the cache and increment the generation, while the new socket then adopted that incremented value as already seen. REST correctly returned 401, but the socket skipped reauthentication until the 60-second periodic deadline.

**Repair:** `crates/otto-server/src/ws_events.rs:52` captures the generation before authentication and carries it into `handle_events`. Its `seen_generation` is initialized from that captured value, so a revoke during lookup, upgrade or startup remains pending. A revoke after a later recheck's pre-await generation read also remains detectable on the following beat.

**Regression/evidence:** `ui_control::events_socket_closes_when_revoked_during_handshake_authentication` wraps the real cached authenticator only at the successful lookup boundary, performs a real token revoke, then returns the previously accepted context. It uses the production router and socket loop. `/tmp/otto-quality-20261007-ws-handshake-red.log` records the expected close timeout before repair. The final focused log records this test passing, as well as both pre-existing cached/uncached logout-close tests.

### R2-C3 [major, resolved] Transient auth failure consumed the pending revocation

The neighboring trace found that the loop acknowledged the new generation and reset `last_check` before awaiting authentication. `still_authorized` mapped `Error::Internal` to true. A transient database/pool failure after cache eviction therefore silently consumed the pending revoke and suppressed another attempt for 60 seconds. This is production-reachable: the cache-miss query in `otto-rbac/src/tokens.rs` maps store errors to `Error::Internal`.

**Repair:** `still_authorized` at `ws_events.rs:146` returns `Option<bool>`: definite authorization/denial is `Some`, transient failure is `None`. The loop at line 206 continues on `None` before changing the seen generation or last-check time. Both changed-generation checks and expired periodic checks therefore retry on the next one-second beat. Definite denial still sends 4401; a transient error alone does not close a valid socket.

**Regression/evidence:** `ui_control::events_socket_retries_revocation_after_one_transient_auth_failure` performs the handshake-time real revoke, injects exactly one transient error on the first socket recheck, then delegates to the real revoked-token lookup. No REST request consumes the injected error. The test requires 4401 within the unchanged budget and exactly three wrapper attempts before any REST assertion: handshake, transient recheck, definite revoked verdict. Thus an implementation that closes immediately on the transient error would also fail. `/tmp/otto-quality-20261007-ws-transient-red.log` records the expected timeout before repair; the final focused log records the regression passing.

**Latest executed verification inspected:** `/tmp/otto-quality-20261007-ws-final-build.log` shows rustfmt check, `cargo clippy -p otto-server --all-targets -- -D warnings` passing, and `cargo nextest run -p otto-server -E 'test(/^ui_control::|^ws_events::|handoff_tests/)'` at **27 passed, 0 failed**, with 1094 unselected tests. **Sibling sampling:** Repository-wide search found no other generation-counter consumers. **Locations:** `examples/plugins/team-performance/lib/view-window.js:23–24`; producer boundary `server.js:1219` and `server.js:1285–1287`.

**Intended:** All time begins with the earliest observed activity belonging to the selected metric corpus. An empty corpus with no linked history gets a zero-length, finite capacity window.

With an empty selected corpus after those global caches exist, the same loop creates a nonempty window. Included records already carry creation/start/completion and Git/deployment timing; raw global side caches do not carry enough ownership information for this new inference. Keep the resolver consistent with the existing metric corpus, including intentionally admitted keyless feature records; do not exclude those solely from the denominator.
