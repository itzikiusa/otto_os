# Usage journal operations and verification boundary

E18 implementation candidate, 2026-10-18. Rust compilation and live ClickHouse verification remain pending the coordinator's Cargo slot. Do not deploy based on this document alone.

The usage engine's data directory now contains `usage-ingestion.sqlite3`. Its SQLite WAL/FULL transaction stores source checkpoint parts and owed events together. sqlx executes SQLite work on its worker thread. The tailer retains a failed batch and retries before consuming more source bytes. ClickHouse delivery starts only after journal commit; acknowledged rows are removed only after INSERT succeeds. Retry uses the stored event ID. `usage_events_durable` uses ReplacingMergeTree and `usage_accounted` unions legacy rows with `FINAL` over the new table, so repeated delivery is counted once before background merges.

Legacy cursor/seen/counter files are read only when adopting the journal. Startup no longer invokes the historical purge/rebuild. Adoption preserves the existing skip-history policy for previously untracked sessions. Journal checkpoints become authoritative after the first successful transaction. Existing legacy ClickHouse rows are unchanged. This is a separate database with additive `CREATE TABLE IF NOT EXISTS` initialization; no otto-state migration number is consumed.

The outbox admits at most 100,000 outstanding rows. At capacity, source progress stops and retries after delivery frees space; accepted events are never discarded to enforce this bound. This is a row bound, not a byte quota: event strings, source-file count, and SQLite's reusable high-water allocation affect disk use. Seen IDs are bounded by the existing 100,000-key cap and eviction allowance; recent Claude corrections by 4,096; Codex counters by 20,000. Source cursors and held responses scale with tracked transcripts, with deleted-source pruning. Seen keys use stable 256-key checkpoint chunks; only changed checkpoint leaves are written. Snapshot creation still traverses bounded dedup state plus tracked files, off the multithread runtime worker. Outbox delivery uses batches of 2,000.

Read cost: `FINAL` applies only to the durable table, whose monthly partitions and `(event_date, session_id, event_id)` order support date/session filtering. Legacy reads retain their existing behavior. This is a design rationale, not a measured performance guarantee: large-data pruning, scanned rows, elapsed time and memory must be measured on isolated ClickHouse before release. Whole-history aggregates still scale with retained data.

Backup and recovery:

1. Back up this journal alongside the usage ClickHouse directory and relevant provider transcripts. Use SQLite's online backup API for a live journal, or stop the daemon fully and copy the DB together with any remaining `-wal` and `-shm` sidecars. Copying only a live main DB can omit committed events.
2. On disk-full or write failure, free space or repair storage and allow the retained transaction to retry. Do not remove the journal or legacy checkpoint files as a recovery shortcut.
3. Corruption or an invalid checkpoint stops ingestion and logs an error; startup does not recreate an empty journal. Preserve the failed DB and sidecars for diagnosis. Restore a consistent backup while stopped, preserving the original event IDs. A stale journal backup is not automatically safe with a newer ClickHouse backup: events already acknowledged after that backup may be regenerated with new IDs. Reconcile source/sink backup boundaries before resuming.
4. Shutdown attempts a bounded journal drain. A timed-out or failed delivery remains pending for restart; it must not be represented as a successful flush. Tailer-held responses are part of the checkpoint, allowing restart recovery even if shutdown does not finish releasing them.
5. Rolling back to an older binary does not understand the new journal/read view and can use stale legacy checkpoints. Schema additions preserve old tables, but ingestion rollback requires a coordinated checkpoint/data plan. Do not run old and new ingestion concurrently.

Required release checks: deterministic transaction-abort/reopen/replay tests; actual disk-full behavior beyond the trigger-based abort simulation; isolated live ClickHouse duplicate replay, parked-budget freshness, repeated schema initialization and shutdown recovery; large-dataset FINAL measurements; daemon lifecycle cancellation during a journal commit; and consistent-backup recovery rehearsal. Never run these against the user's real usage database.
