## Ranked findings

### P4-01 [major] Workflow version history retrieves every full graph to display a metadata list — `crates/otto-state/src/workflows.rs:820`

**What:** `list_versions` selects every column from every saved version, fetches all rows, and parses each graph. The HTTP handler returns the full snapshots. The Versions drawer uses only version, note and timestamp, plus the version number for Restore. Each graph/instructions edit appends another snapshot, so opening or refreshing this drawer grows with all historical bodies even when none is being inspected.

**Cost:** V = retained revisions of one workflow, B = mean graph/instructions size. A drawer load reads, parses, reserializes, transfers and retains O(V × B) body bytes, plus O(V) rendered rows. This is one growing query, **not N+1**. At B = 100 KiB, V = 100/1,000/10,000 means approximately 9.8/97.7/976.6 MiB of historical body content per load, before parsed-object/string overhead. These are payload calculations, not RSS or measured latency. A prompt-rich workflow edited repeatedly can accumulate revisions; no version-count or aggregate-history limit was found. The path is warm, user-triggered history browsing; it is not idle polling. Major is warranted for the 1,000-revision scenario; no claim is made that typical current histories have that size.

**Evidence: confirmed source trace.** SQL has no `LIMIT` (`workflows.rs:821–828`); `row_to_version` parses `graph_json` and retains instructions (`:55–69`). The route returns `Vec<WorkflowVersion>` unchanged (`crates/otto-server/src/routes/workflows.rs:134–142`). `WorkflowVersion` contains graph and instructions (`crates/otto-core/src/workflows.rs:503–520`). Updates append snapshots (`routes/workflows.rs:111–128`), and the migration explicitly defines append-only history (`crates/otto-state/migrations/0089_workflow_orchestrator.sql:18–33`). The existing `(workflow_id, version DESC)` index supports ordered paging: this is not a missing-index allegation. The UI loads the complete response (`ui/src/modules/workflows/WorkflowsPage.svelte:1520–1535`) and renders metadata only (`:2083–2091`). A separate authorized full-version endpoint already exists (`routes/workflows.rs:145–158`); Restore already retrieves its own snapshot server-side.

**Fix/payoff:** Add thin version summaries and keyset paging by descending version, with a bounded page size and bounded displayed history window. Retain the individual full-version and Restore behavior, preserve access to the oldest revision, and update contracts/types with the API. A P-row history page costs O(P × metadata), independent of B and total V, instead of O(V × B). Only explicit snapshot inspection needs O(B). Do not prune or delete history to achieve this. Coordinate `WorkflowsPage.svelte` behavior edits with Claude's reserved route-selection/presentation work and the separately tracked atomic-version correctness repair.

**Regression/measurement:** In isolated state, seed distinct 100 KiB graph/instruction bodies at V=100/1,000, and a larger thin-history case for paging. Assert the list omits graph/instructions, newest/oldest navigation has no gaps or duplicates, and Restore from a later page uses the correct original snapshot and creates a new version. Add a new save between page reads. Browser checks should bound mounted history rows, preserve selection and Retry, and observe metadata-sized network responses. Record endpoint bytes, drawer interaction latency, daemon/renderer CPU and post-close heap/RSS, including N=1/3/5 background sessions. None of these executions occurred in this review.

### P4-02 [minor] Shared workflow node bodies outlive their views with only an entry-count bound — `ui/src/modules/workflows/runProgress.ts:97`

**What:** The app-wide `SharedNodeBodies` retains the newest full body for each visited `(run,node)` until 48 different keys displace it. It has no byte budget or expiry, and its `clear()` method has no production caller. Leaving the workflow or switching workspace therefore leaves completed bodies reachable. `RunBodyCache` separately limits inactive bodies to 16 entries/16 MiB, but evicting from that cache does not release the shared cache's reference.

**Cost:** K = distinct completed node keys visited in this webview, B = average full node-body size. Shared retained content is O(min(K,48) × B). Forty-eight 1 MiB bodies retain approximately 48 MiB of serialized-equivalent content after the views close; actual JS heap depends on string/object representation and must be measured. This is a bounded-count cache, **not an unbounded leak**. The warm inspection scenario is a series of node selections or expansions across runs. It does not require simultaneous expansion of 48 nodes. Arbitrary transform JSON becomes full node output (`crates/otto-server/src/workflow_engine.rs:3636–3651`), and the detail endpoint returns the complete selected node (`crates/otto-state/src/workflow_progress.rs:446–488`), so a 1 MiB body is not excluded by a summary projection. Sizes remain a synthetic scenario rather than known user data. Minor reflects the 48-entry ceiling and manual inspection frequency.

**Evidence: confirmed lifetime/reference trace.** `done` stores full bodies (`runProgress.ts:98`, `:115–119`), constructor cap defaults to 48 (`:101`), and the singleton is module-scoped (`:144–145`). `peek` returns those bodies directly (`:104–106`). Both RunSteps and the node inspector use the shared fetch (`RunSteps.svelte:225–233`; `WorkflowsPage.svelte:142–154`). The separate inactive-byte eviction is `runProgress.ts:78–84`; changing runs clears only that local cache (`RunSteps.svelte:263`). Repository search found no `sharedNodeBodies.clear()` call. Inspector cleanup aborts its request (`WorkflowsPage.svelte:161`) but does not evict completed entries.

**Fix/payoff:** Give the shared completed cache both a byte and entry budget; do not cache a body larger than the whole inactive budget. Preserve in-flight request sharing and version checks. Optionally release inactive completed bodies on last-view departure, without aborting another mounted consumer. An explicit 16 MiB budget makes inactive shared residency O(16 MiB), rather than up to 48 arbitrarily sized bodies. Existing consumers may retain their currently displayed object; no data should be truncated or removed from persistence.

**Regression/measurement:** Fetch 48 distinct large bodies sequentially, close their views, and assert completed-cache accounted bytes stay within the chosen budget. A too-large result must still display, be returned to all simultaneous consumers, and remain uncached afterward. Assert both consumers still share one request and revisiting an evicted node reloads the correct version. Record forced-GC heap and renderer RSS at 0/16/32/48 visits and after leaving Workflows; do not call serialized-byte accounting a measured heap limit.
