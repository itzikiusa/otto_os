## Ranked findings

### [MAJOR] R4-P2-PERF-01 — Working diff buffers every untracked patch before applying response limits — `crates/otto-git/src/local.rs:2221`

**What:** Full `Working` diff collects all per-file stdout buffers into `Vec<Vec<u8>>`, then concatenates them into another buffer. Only afterward does `diff_with` apply the parser's display budget. Eight-way concurrency limits simultaneous children, not retained bytes or total children. The existing 128 MiB stdout ceiling is per subprocess, so it never sees the aggregate.

**Cost:** N is the number of untracked, nonignored paths; B is each patch's byte size. Each request performs N diff subprocesses plus the tracked diff and untracked listing, retains approximately N×B patch bytes before parsing, and performs another N×B copy into the aggregate (with overlapping buffers and spare capacity). At N=100 and B=4 MiB, the collected buffers alone are 400 MiB even though the ordinary HTTP result's hunk-content budget is 4 MiB. Doubling N doubles memory and child work; eight concurrent requests can retain roughly 3.2 GiB just in collected patches at that phase. This is a warm full-diff API path, not the default windowed per-file UI path; no production frequency is claimed.

**Evidence: confirmed by hand trace.** `diff_with` first obtains the full byte vector at `local.rs:2164` and only then calls `parse_diff_bytes_capped` at `:2167`. The untracked list is not row-capped (`:2330–2335`); `buffered(8).try_collect()` retains all individual stdout buffers (`:2221–2230`), followed by `extend_from_slice` (`:2231–2232`). The subprocess ceiling is `local.rs:233`. Reachable HTTP request: `GET /repos/{id}/diff?target=working`; omitted `summary` defaults to false and ordinary caps are selected at `crates/otto-git/src/http.rs:1449–1455`, then the route executes this path at `:1615`. `DiffCaps::DEFAULT` allows 4 MiB hunk content (`crates/otto-git/src/parse.rs:616–623`). The UI's normal summary/per-file loader is a real mitigation, not a global guard on this route. This closes the prior review's explicitly deferred aggregate-diff question with its caller and budget trace.

**Fix and payoff:** Add an aggregate raw-byte admission budget during collection, consume finished patches incrementally instead of `try_collect`, and stop/cancel remaining read children when the budget is exhausted. For capped HTTP responses, retain file metadata through the existing summary representation and mark remaining hunks omitted; never silently return a semantically complete partial patch. Internal complete-diff callers need an explicit resource-limit error or a separate streaming implementation. With aggregate budget R and concurrency W, retained collection bytes become O(R + W×bounded-per-file-buffer), independent of N, and unnecessary later patch subprocesses can be skipped. Simply removing `try_collect` while retaining unlimited aggregate output is insufficient.

**Regression/measurement plan:** An isolated temporary repository with many modest untracked files should exceed a deliberately small injectable aggregate budget while every file stays below the per-spawn cap. Assert admitted bytes/peak live buffers and child launches remain bounded, truncation/error is explicit, metadata and small/per-file diffs remain correct, and cancellation kills outstanding read children. Measure daemon peak RSS and duration at N=10/100/1,000 with one and two full-diff requests. Do not use the user's repository to generate test files.

### [MAJOR] R4-P2-PERF-02 — Workbench history reloads and mounts its entire lifetime timeline — `crates/otto-state/src/workbench.rs:678`

**What:** Revision history is intentionally append-only, but the read API has no cursor or limit. Opening history loads every revision, and every new head revision reloads the full list. The UI mounts one full row and `RelTime` component per revision, plus one comparison option per revision after selection. This combines unbounded network/serialization work with an unbounded DOM on a recurring editing path.

**Cost:** N is lifetime revision count for one document, independent of document body size. A load costs one ownership query plus one indexed query returning N metadata rows, O(N) wire/decoding work, and O(N) mounted rows/components. Each metadata row carries a 64-character content hash (`workbench.rs:108–116`), so hashes alone contribute 0.64 MB at 10k revisions or 3.2 MB at 50k, before dates, keys and other values. At 10k revisions the row markup creates at least 70k elements and 10k `RelTime` instances, with another ~10k options when comparing. Autosaves coalesce only within 60 seconds; one revision/minute during eight-hour active editing produces roughly 480/day, making 10k revisions about 21 such days. Checkpoints can grow faster. With history left open for H new revisions, the repeated loads process H×N + H(H+1)/2 metadata rows. This is a warm history-open path; coalesced saves that keep the same head seq do not trigger that reload.

**Evidence: confirmed by hand trace.** `list_revisions` performs `SELECT * ... WHERE doc_id = ? ORDER BY seq DESC` then `fetch_all` (`workbench.rs:676–683`). The `(doc_id, seq)` primary key already supports paging (`crates/otto-state/migrations/0165_workbench.sql:37–48`), so this is not a missing-index claim. Coalescing is 60 seconds (`workbench.rs:32`, `:343–377`); revisions are not aged out by retention. `ui/src/modules/workbench/HistoryPanel.svelte:53–54` loads all rows, `:63–68` reruns on head changes, `:170–190` renders all rows, and `:206–208` renders the full comparison list.

**Fix and payoff:** Add bounded `limit` and `before_seq` history paging on the existing primary key, refreshing only the newest page/head metadata when saves occur. Window the retained timeline and provide searchable/paged access to older comparison revisions rather than a full native select. Preserve all stored history and direct revision restoration. Initial work becomes O(P) rows/bytes for page size P (for example 100), with O(visible rows) DOM, rather than O(N) per open/save. Extend the API contract/types in lockstep; do not solve this by deleting history or hiding older revisions.

**Regression/measurement plan:** Seed isolated SQLite with 50k revisions sharing small content blobs. Assert newest-page size, contiguous descending cursors, oldest revision reachability, and stable paging across a new save. Browser test should open history, select and compare an older revision, save while open, and assert bounded rendered row/option count and bounded GET payloads. Measure renderer CPU/RSS and click-to-history latency at N=100/10k/50k; expected cost should follow page/viewport size, not N.
