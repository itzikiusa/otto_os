## R4-P5-01 recap proposal before backend mutation

Current trace: RecapPanel polls full detail every four seconds. `recap::get_archive` calls `Store::get`, which calls `ensure_index`; `Archive::detail` reads/parses the visible JSONL page and reads draft.json. Merely adding a status endpoint around that helper would conceal cold index work and would not meet the repair.

Proposed new owner-checked revision route uses `Store::load` and owner validation directly, skipping `get`, `ensure_index` and `detail`. It returns cloned cached metadata, event extent/revision and a draft stamp made from high-resolution mtime, length and file identity. Stat calls do not read/hash event or draft bodies. A cold status read may load small metadata once; repeated checks must have zero JSONL/draft body reads and never initialize the sparse event index. Same-size atomic draft replacement, in-place changes and deletion must change the stamp. New metadata, capture/generation/error state and event extent remain observable after stopped capture.

Tests to author before mutation: isolated 1/100-event archives with 2/20 KiB payloads; 15 unchanged status reads have zero instrumented body reads/parses, no indexing and bounded response bytes. Cold-store status remains unindexed; owner mismatch fails. Same-size rename replacement, in-place rewrite and deletion change draft revision. Existing full-detail paging and metadata remain correct. Route/policy/contract test must exercise the actual authenticated route so a policy omission cannot be hidden by archive unit tests.

UI acceptance: initial load/page navigation/explicit Refresh fetch detail. Visible polling/resume checks only revision. New events change the newest incomplete page; an older complete page stays immutable while metadata updates. Changed draft revision fetches new draft/body, including another client's regeneration and supported manual draft changes. Capture or summary status alone updates metadata without rereading identical event content. Two-phase revision/detail races must not record a newer revision against an older body: compare a response-coupled stamp or recheck and retry safely. Failure, cancellation, hidden/resumed window, missed events and unmount must remain covered.
