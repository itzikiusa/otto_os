## Ranked finding

### [MINOR] R4-P5-01 — Completed room recaps keep retransferring unchanged event bodies — `ui/src/modules/rooms/RecapPanel.svelte:17`

**What:** The mounted panel starts a four-second `pollWhileVisible` chain that calls the full detail loader unconditionally unless a local action is busy. It continues when capture is stopped and summary generation has finished, and when the selected tab only displays the summary. Each result replaces `detail` even if unchanged. Visibility handling and non-overlap are useful existing mitigations; they do not remove work while a completed recap is open in a visible window.

**Reachability/evidence: confirmed by source trace.** `RecapPanel.svelte:17–18` always requests `?after=<cursor>&limit=100`. The HTTP detail handler at `crates/otto-server/src/rooms/recap/http.rs:195` obtains the archive and calls `a.detail`. At `crates/otto-server/src/rooms/recap/archive.rs:380–420`, detail seeks using a sparse index, reparses the requested events and reads/deserializes `draft.json` whenever present; the result is then serialized and sent again. The browser decodes base64 terminal payloads in `RecapPanel.svelte:24` and renders them in the event loop at `:56`. Terminal capture stores actual PTY bytes as base64 (`crates/otto-server/src/rooms/recap/mod.rs:346–366`), so a page can contain substantially more than tiny metadata records. No request/CPU benchmark was executed for this finding.

**Cost:** Let P≤100 be displayed events, B their serialized payload bytes, D the draft bytes and K the visible poll count. Sparse indexing limits a normal page read to at most P+127 parsed events; this is **not** a full-archive scan. Polling still does O(K×(page bytes + D)) disk parsing, serialization and transfer for an unchanged page. Ignoring request duration, K approaches 900/hour. A modest fixture of 100 events averaging 2 KiB therefore retransfers approximately 176 MiB/hour in event payload alone; ten times the average event size gives ten times that payload cost. The page interval remains fixed and the row count is bounded, so this is a minor warm-view repeated-work issue, not an unbounded-memory blocker. Summary-only viewing pays the event-body cost too.

**Fix and payoff:** Use a lightweight metadata/revision check that does not call `get`/`detail` or reindex/reparse event bodies; fetch the visible event page and draft only when relevant revisions change. Separate metadata, event-page and summary revisions, or include them in one cheap conditional response. A stopped capture can still have its summary regenerated from another client: do not permanently stop observing it merely because it is currently terminal. Preserve visibility into external/manual changes according to the archive's supported change contract, for example with draft mtime/revision checks plus a bounded fallback and explicit Refresh. During active capture, an earlier complete page is immutable; update metadata without repeatedly retrieving that older body. Unchanged page-body work becomes one initial O(B+D) fetch plus O(K) small revision checks, instead of O(K×(B+D)); full bodies transfer again only when their content changes.

**Regression/measurement plan:** With isolated archives, hold a stopped/completed recap open for 60 seconds and count detail-body bytes, JSONL reads and draft reads; verify that repeated unchanged checks do not reread/retransfer the body. Test active capture at the newest page, an immutable older page, summary-only viewing, same-client and second-client regeneration, generation failure/cancellation, explicit refresh, hidden/resumed windows, reconnect/missed events and unmount with an in-flight request. Confirm a new draft becomes visible after external revision changes. At P=1/100 and average event payloads 2/20 KiB, compare daemon and renderer CPU/RSS plus response bytes and navigation latency. Keep source/browser mode constant. Measure the proposed small-check endpoint separately so a nominal metadata API does not conceal the same underlying detail scan.
