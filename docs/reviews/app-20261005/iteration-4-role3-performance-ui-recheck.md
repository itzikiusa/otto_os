## Findings

### R3-UI-01 [major, correctness of bounded pagination] Importing into a full page drops a reachable item without updating its cursor — `ui/src/lib/stores/product.svelte.ts:575`

**Trace:** Load exactly 50 summaries: `transcriptNextCursor` is null. `addTranscript` prepends the successful POST result and slices the array back to 50, discarding the former 50th item. It does not update or reload cursor state. Both navigation buttons remain absent (`ui/src/modules/product/OverviewTab.svelte:1510–1514`). The dropped item is still stored but cannot be reached through the list until reopening/reloading or using search. With more than 50 initial rows, the old cursor still points after the discarded boundary item, so Next skips it. The active page can also be an older page when a new newest transcript is prepended.

**Cost/spec implication:** P=50 is correctly bounded in memory, but the implementation meets that bound by discarding list reachability. The repair must preserve all history while remaining O(P), not restore eager full-history loading. This is an acceptance seam introduced by the performance repair, not a new claim about backend data loss.

**Fix/payoff:** After a successful import, reload a coherent first summary page and its matching next cursor (or implement an explicitly separate pinned new item without dropping a cursor-covered item). Invalidate pending summary-page ownership appropriately. One extra bounded summary request preserves reachability; metadata remains O(P).

**Required regression:** Actual store POST flow starting with exactly 50 rows, then 51 and 100; import on first and older pages, navigate forward/backward and assert every existing ID remains reachable exactly once in ordinary pages. Include delayed pre-import page completion. `productTranscriptLoading.test.ts` currently provides only GET transport and does not exercise import or mutation of a full page.

### R3-UI-02 [minor, performance/lifecycle] Departing an async provider does not stop its remaining search-page requests — `ui/src/lib/findProviders.ts:57`

**Trace:** The unregister function only deletes the provider from the Set; it does not call `release`. Switching Product tabs unmounts Overview (`ProductPage.svelte:843–847`) while `ProductStore.changeTab` leaves story identity/generation intact (`product.svelte.ts:241–244`). A pending `searchTranscripts` therefore continues to satisfy `current()` and follows subsequent cursors (`:536–552`). Its abort signal belongs to FindInPage, which checks provider identity only **after the complete provider promise returns** (`FindInPage.svelte:233–235`). The Product release hook would invalidate the search generation (`product.svelte.ts:561–563`), but it currently runs only when find closes, not when Overview unregisters.

**Cost:** If a search has K remaining server pages when the user leaves Overview, it can still issue K serial HTTP requests and retain its matching metadata, rather than stopping after the one already in flight. For example, a controlled search response with 100 one-occurrence summaries per page can issue up to 50 pages before the 5,000-match cap; leaving after page 1 needlessly permits 49 more. Backend scan cost/latency is not asserted because those routes are not implemented yet. This is avoidable interactive work after consumer departure, even though result publication is eventually guarded.

**Fix/payoff:** Release/cancel provider-owned search work on unregister, preferably invalidate/abort the active provider operation immediately. Product generation invalidation alone already prevents its next cursor request after the pending response resolves. Follow-up calls become zero after departure rather than O(K); keep the stale-result/error guards too.

**Required regression:** Use the real registry cleanup plus Product search loop with a deferred page carrying `next_cursor`; unregister Overview without changing the selected story, resolve the page, and assert no second GET and no retained old search rows. Repeat with rejection, tab return, query replacement and find close. Existing `asyncFindProvider.test.ts:50–56` substitutes a provider and proves stale-error suppression; it does not exercise unregister cleanup or cessation of paged transport.

### R3-UI-03 [minor, cancellation correctness] Closing search while its selected body loads still expands the old hit afterward — `ui/src/modules/product/OverviewTab.svelte:1045`

**Trace:** A successful search starts `goTo(0)` (`FindInPage.svelte:276`), which awaits the provider's reveal and a network body fetch. Close/dropRanges aborts search and releases its row mapping, but does not change `navSeq` (`:61–70`, `:323–342`). Overview's reveal captures only `selectedId`; when the body completes with the same story selected it unconditionally sets `expandedTranscripts[t.id] = true` (`OverviewTab.svelte:1043–1048`). Thus a canceled search can expand a transcript after the bar closes. Replacing the query with a no-results query has the same gap: there is no new `goTo` to invalidate the old navigation. Store body publication is correctly story-scoped; the missing boundary is the search/reveal lifetime.

**Cost/spec implication:** The retained cache still stays bounded. The issue is an obsolete network completion applying view state after cancellation, not an alleged memory leak. It matters specifically because body reveal is newly asynchronous.

**Fix:** Give reveal/navigation the current search lifetime or cancellation signal and check it after await before expansion, highlights or scroll. Invalidate navigation on close/new search as well; fencing only `goTo` after reveal is too late to prevent Overview's expansion side effect.

**Required regression:** Complete search metadata, defer its selected-body GET, close find or replace the query with a no-results query, then resolve the body. Assert no expansion/highlight/scroll from the departed search. Keep normal find→expand and new-search→reveal controls. Current async-find tests replace `goTo` with an empty function (`asyncFindProvider.test.ts:17`), so their close test cannot establish this behavior.

### R3-BE-01 [minor] Summary byte counts still load the selected page's body payload inside SQLite — `crates/otto-state/src/product.rs:1803`

**What:** The response omits `body`, but calculates `body_bytes` using `length(CAST(body AS BLOB))`. The cast prevents SQLite's direct-column byte-length optimization. This does not restore the old whole-history wire transfer; it leaves avoidable body work within each bounded summary query.

**Evidence:** Confirmed source mechanism, not measured elapsed time. `Cargo.lock:2896` and `:6178` select `libsqlite3-sys 0.37.0` and `sqlx-sqlite 0.9.0`. Root Cargo enables SQLx's `sqlite` feature; installed `sqlx-0.9.0/Cargo.toml:181` maps that to bundled SQLite. In the installed bundled `sqlite3.c`, line **116829** describes avoiding data loading for length/type/byte-length functions, but lines **116837–116846** apply the column flag only when the immediate argument is `TK_COLUMN` or `TK_AGG_COLUMN`. `TK_CAST` instead compiles its ordinary operand before `OP_Cast` at **116587–116594**. The overflow-column path at **98530–98555** skips content only with the applicable flag and otherwise reads the overflow payload. Dependency source inspected under `/Users/itziklavon/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/`; no different system SQLite was used to infer this behavior.

**Cost:** P is the requested page size, clamped to 1–100, and the query fetches P+1 for continuation. With the UI's P=50 and 256 KiB bodies, up to **12.75 MiB** of body payload is processed inside SQLite per open/page, although only summaries cross SQLx/HTTP. At 1 MiB bodies that becomes **51 MiB**. This is O(P×B) selected-body work, bounded independently of total history N; it is not O(N×B). Physical disk bytes depend on page cache and storage and are **not** established by these arithmetic examples. Warm navigation/import refresh is enough to encounter the work, but its measured local impact is unknown, so minor rather than major.

**Fix/payoff:** Prefer a direct byte-length primitive supported by the shipped SQLite, such as `octet_length(body)`, whose direct-column `BYTELENARG` optimization is present in the same source, or stored byte metadata if a broader compatibility requirement precludes it. Preserve UTF-8 byte semantics rather than substituting text character length. Confirm actual VDBE flags and file-backed behavior before selecting the repair. This should remove overflow-body loading solely for size calculation while retaining O(P) metadata and the existing cursor protocol. Do not edit migration 0171 merely to hide the projection cost.

**Required verification:** On the application's linked SQLite, inspect `EXPLAIN` for the current and replacement projections (including the Column P5 flags); compare empty, ASCII, multibyte Unicode, embedded-NUL and large text sizes against exact UTF-8 byte length. Seed distinct 256 KiB/1 MiB bodies in a throwaway file-backed database, use equal P with increasing total N, and record warm/cold-ish query latency plus connection cache hits/misses or VFS bytes. Retain the current actual HTTP response-size assertion. A small JSON response or an index-name-only `EXPLAIN QUERY PLAN` does not establish that body payload was not loaded.

### Design metadata lock scope

Canonical-root/artifact mutexes serialize one artifact's read/merge/write/publication (`service.rs:80–99`, `:1237`, `:1290`); they are not one global lock held over all artifacts. The short registry mutex prunes weak entries only after async filesystem identity resolution. Metadata reindex normally reuses an FTS body capped by extraction's **64 KiB** text limit (`extract.rs:24`, `service.rs:1176–1180`), rather than reparsing a 25 MiB head on every title change. Cache-miss reindex can still read/extract the head. Content commits keep the same-artifact lock during offloaded validation/hash/reindex (`:687–723`, `:803`); offloading avoids runtime CPU blockage but does not eliminate lock wait. Thumbnail upload holds it over a ≤2 MiB blob write and cleanup (`:1789–1807`). Approval also includes consumer notification: one incoming-link read plus one artifact lookup per distinct consumer (`:1192–1208`).

These scopes preserve required publication order. No new confirmed hotpath lock defect is asserted without a same-artifact contention/fan-in workload. Do not release the lock early in a way that reintroduces acknowledged metadata loss or stale index/event publication. Root's current Design run was mixed (125 passed/3 adjacent-writer failures); in-progress importer/thumbnail repairs and their correctness acceptance remain owned elsewhere, not certified by this performance pass.
