## Ranked findings

### [major] Busy pooled MCP connections spill into an unbounded number of fresh processes — `crates/otto-mcp/src/client.rs:205`

**What:** Two parked sessions are a reuse limit, not a concurrency limit. When both are busy for 250 ms, `checkout` returns `None` and `op` calls `one_shot`, which opens another transport session. For stdio that spawns another complete MCP server process. There is no admission semaphore in this client path.

**Cost:** N = simultaneous operations against one configured MCP server whose responses take longer than the busy wait. With two occupied parked sessions and N further operations, there can be 2 + N child processes/connections and N additional initialize handshakes. At eight total callers, up to eight server processes execute; at twenty, up to twenty. Peak child memory is approximately N × M, where M is the external server's resident footprint (not measured here); repeated overlapping bursts also pay repeated process/package initialization. This is hot per-tool execution under the app's supported multi-agent workload. The 20-second operation timeout limits duration, not parallel count.

**Evidence: confirmed control-flow trace.** `client.rs:47–49` declares two slots and the 250 ms wait; `client.rs:146–160` returns no slot when all remain busy; `client.rs:249–251` opens the one-shot; `client.rs:288–300` spawns stdio. The service's 32-client pool cap (`crates/otto-mcp/src/service.rs:60–61`) bounds parked configured-server clients, not these temporary sessions.

**Fix/payoff:** Give each configured server a bounded permit pool shared by pooled operations, initialization, and any one-shot fallback; add a total process budget if many servers may be active. Queue with cancellation and a deadline or return a clear busy response when the queue is full. Preserve the existing no-replay rule for requests that might have reached the server. At cap C, active transports/processes become O(C) rather than O(N), and bursts reuse initialized sessions instead of spawning N−C fresh servers. A configurable cap can preserve servers that benefit from more than two sessions.

**Regression verification:** A lightweight stub holding responses open should show a fixed child/connection count at N=1,2,8,20, cancellation should release permits, and a queued request must execute at most once. Record parent/child CPU and RSS over repeated bursts.

### [major] MCP's 1 MiB response cap is checked after unbounded buffering — `crates/otto-mcp/src/client.rs:471`

**What:** HTTP uses `resp.bytes()` before checking the response length. Stdio uses `read_line` before checking cumulative bytes (`client.rs:515–523`). One large JSON line or a stream without a newline can allocate far beyond the declared cap before rejection. This affects initialization, tool discovery, and tool results.

**Cost:** B = bytes returned by the configured server before EOF/newline; N = concurrent operations. Actual buffer memory is O(N × B), not O(N × 1 MiB). A 100 MiB response allocates roughly 100 MiB before rejection; eight simultaneous such responses imply roughly 800 MiB of payload buffers, before allocator overhead or other copies. A never-ending body/line grows until timeout; the 20-second timeout is not a byte bound. Large tool results and noisy servers are plausible inputs; no such response was sent during this review.

**Evidence: confirmed read/check ordering.** `client.rs:43` declares `MAX_BODY_BYTES = 1024 * 1024`; `client.rs:471–474` buffers HTTP first; `client.rs:511–524` buffers the entire stdio line first. The timeout surrounding `run_on` (`client.rs:214`) does not change that allocation behavior.

**Fix/payoff:** Read HTTP chunks and reject before appending past the remaining budget (also reject an excessive declared content length early). Read stdio through a limited reader or bounded `fill_buf`/consume loop, stopping after cap + 1 bytes, including across skipped notifications. Discard the poisoned transport after overflow so unread bytes cannot become a subsequent response. Memory becomes O(N × cap), approximately 1 MiB per active read instead of arbitrary B. Streaming SSE framing should use the same cumulative budget.

**Regression verification:** Chunked HTTP without Content-Length, a long newline-free stdio response, one oversized line, and many small notifications must reject after bounded consumption. Sample RSS with concurrent readers; do not allocate a huge fixture just to prove the limit.

### [major] Scheduled shell runs retain all output until completion and copy it into the report — `crates/otto-server/src/scheduled_tasks_engine.rs:960`

**What:** `run_shell_once` pipes both streams into `wait_with_output`; no byte cap or spool file is used. `shell_report` subsequently formats both full buffers into one report. Process-group cleanup and a time limit are implemented, but output memory remains unbounded by bytes.

**Cost:** R = aggregate stdout/stderr bytes per second, T ≤ 300 seconds, C = active runs (default 2). Capture alone retains approximately C × R × T bytes. At 1 MiB/s for five minutes, one task reaches about 300 MiB and two reach about 600 MiB before vector capacity overhead. Successful report construction adds another output-sized allocation while the original `Output` still exists; invalid UTF-8 can add decoding allocations. A verbose build, repeated log command, or accidental endless-output command can therefore pressure the desktop daemon despite the concurrency limit. These are cost illustrations, not measured throughput.

**Evidence: confirmed execution trace.** `scheduled_tasks_engine.rs:65` sets 300 seconds; `:160–168` sets default concurrency two; `:851–861` acquires that permit for shell execution; `:947–960` pipes and buffers both streams; `:1257–1269` embeds both complete streams into a new string. Retries are capped at six, which bounds attempts but does not fix per-attempt memory.

**Fix/payoff:** Drain stdout and stderr concurrently into bounded head/tail buffers and mark omitted bytes in the report, or stream into quota-limited report files and return a bounded preview. Continue draining/discarding after a preview cap so a child cannot block on its pipe; enforce a disk quota if spooling. Keep process-group cancellation and exit semantics. With a 1 MiB combined preview budget per run, retained capture/report memory is O(C MiB), independent of R × T.

**Regression verification:** Use a small deterministic over-limit producer on both streams; assert bounded capture, truncation metadata, preserved exit status, timeout/cancellation cleanup, and no pipe deadlock. Parent should repeat at N=1/2 permitted runs while recording daemon RSS over time.

### [major] MCP tool access loads one capability request per tool and keeps refreshing every visited tool — `ui/src/modules/mcp/ToolsTab.svelte:48`

**What:** Opening a tool catalogue calls `resourceAccess.load` once per tool. Each capability response runs five operation checks; `ResourceAccess::preview` reloads the same user's groups for every operation. The global access cache then retains those tool entries and rechecks all of them on its safety/fallback refresh even after the Tools tab is gone. The shared limiter prevents a socket storm but does not batch or eliminate this work.

**Cost:** T = tools in the discovered catalogue; V = tool entries accumulated from catalogues visited in this webview. A cold Tools open makes T child capability HTTP requests (plus the tool list and possibly a server-level capability request), with at least 5T group-membership queries inside those child requests. T=200 means 200 child requests and at least 1,000 repeated membership reads; T=1,000 means 1,000/5,000. Only three loads are admitted concurrently, so the first example requires at least 67 request waves. Afterwards each full safety refresh costs V requests, with concurrency two; the connected safety interval is five minutes, the disconnected fallback 15 seconds, and hidden-window work is paused. No throughput/latency measurement is claimed.

**Evidence: confirmed UI→route→DB trace.** `ToolsTab.svelte:48–52` loads every tool; `ui/src/lib/stores/resource-access.svelte.ts:23,77–81` applies the limiter, while `:119–146` retains/rechecks entries without a view-owner release. `crates/otto-core/src/access.rs:212–218` lists five MCP operations; `crates/otto-server/src/routes/resource_access.rs:455–456` calls preview per operation, and `crates/otto-rbac/src/resource_access.rs:69` queries memberships each time, even for root/legacy evaluation. The backend MCP list already batches visibility evaluation via `resource_allowed_under` (`crates/otto-mcp/src/service.rs:191`), but its response does not supply these UI capabilities.

**Fix/payoff:** Return per-tool effective capabilities with the authorized tool catalogue or expose a bounded batch endpoint. Read policy and caller memberships once per server request and run the pure evaluator for each child/operation, preserving all page/workspace/feature checks. Track mounted consumers or evict unused capability entries so background refresh covers visible resources. Initial HTTP fan-out becomes one catalogue/batch request instead of T requests, and invariant membership reads become O(1) per batch instead of 5T. Decision evaluation itself remains O(T × operations × policy size), as required.

**Regression verification:** Seed 200/1,000 tools, count HTTP and SQL reads on initial open and a safety refresh, then leave the page and verify unused child decisions are not repeatedly fetched. Check child-specific deny precedence, group changes, root/legacy behavior, and identity changes.

### [minor] Mission Control manual refresh awaits up to 500 individual usage queries — `crates/otto-server/src/workgraph_projector.rs:882`

**What:** The refresh route awaits `refresh_session_costs`, which lists up to 500 projected items and calls the single-session usage aggregate serially for each session/external-trigger item. The default background reconcile correctly excludes these queries; this issue is limited to the explicit refresh action.

**Cost:** S = eligible session items among the selected 500, so 0 ≤ S ≤ 500. One refresh performs S serial ClickHouse query round trips plus any changed-cost SQLite writes. With S=100/500 and an illustrative 10 ms mean aggregate latency, the serial dependency contributes about 1/5 seconds before the HTTP response, excluding backfill work. This latency is illustrative, not measured. The path is warm/manual and bounded, so minor rather than a hot-path blocker.

**Evidence: confirmed call chain.** `crates/otto-server/src/routes/workgraph.rs:265–267` awaits all work before response. `workgraph_projector.rs:873–883` applies the 500-item bound and serial loop; `:800–804` filters eligible kinds and queries usage. `crates/otto-usage/src/engine.rs:1103–1130,1559–1563` executes one uncached per-session query. Current usage code uses the persistent ClickHouse server; old projector comments about one `clickhouse local` spawn per call are stale and are NOT evidence for process-spawn cost.

**Fix/payoff:** Add a scoped multi-session totals method using `WHERE session_id IN (...) GROUP BY session_id`, map results to projected items, and persist only changed costs. Session IDs already come from workspace-scoped items. S usage round trips become one (or a small bounded batch), retaining the same per-session totals and missing-data behavior. Do not substitute a date-limited or row-limited global dashboard rollup if it changes lifetime totals.

**Regression verification:** A 500-session fixture should produce one usage request and correct independent lifetime totals, including missing usage and zero cost. Verify workspace isolation and unchanged-cost no-write behavior.
