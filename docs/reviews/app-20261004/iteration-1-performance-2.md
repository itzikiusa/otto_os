## Ranked findings

### [MAJOR] P2-PERF-01 — Sparse Mongo results bypass the response budget when expanded into a grid — `crates/otto-dbviewer/src/drivers/mongodb.rs:3571`

**What:** `collect_docs` charges the size of each original BSON document, but `docs_to_result` subsequently creates one JSON value for every unioned column in every row, filling absent fields with `null`. The 500-column union cap bounds width, not the row × width product. The generated padding is never charged to the 32 MiB result budget.

**Cost:** Let N be fetched documents and C the unioned column count (up to 500, plus the spill column). Retained source payload can be O(N) for documents containing `_id` and one rotating field, while output allocation and serialization are O(N×C). At N=100,000 and C=500, the code constructs 50 million values, roughly 49.8 million of them null for two-field documents. The nulls alone occupy about 249 MB in JSON (`null` plus delimiter), before useful fields, response buffers, or the webview's decoded arrays. N=1M multiplies that tenfold. A result comfortably below 32 MiB in source form can thus impose hundreds of MB of wire data and far larger resident allocations on one desktop. This is a warm, ordinary query path when selecting “All,” not a fabricated API-only input.

**Evidence: Confirmed by hand trace.** UI “All” sends 1,000,000 rows (`ui/src/lib/stores/database.svelte.ts:102`, `:3177`). `collect_docs` charges `approx_doc_len` before conversion (`mongodb.rs:3483`); that estimator only visits existing fields (`:3518`). Column union stops at 500 (`:3506`, `:3557`), then every document iterates the entire union and inserts `Value::Null` for each missing field (`:3568`, `:3571`, `:3578`). No second output budget is applied before returning rows (`:3601`). The nominal budget is 32 MiB (`crates/otto-dbviewer/src/types.rs:1695`). Offloading conversion to the blocking pool protects runtime workers but does not bound these allocations.

**Fix:** Enforce the budget against the final rectangular representation before allocating all rows. Once the column union is known, charge each prospective row including null padding, delimiters and actual cell payloads, stop at the budget, and mark byte truncation. Also enforce a resident cell-count budget because a null value costs more in memory than its JSON representation. Keep source collection bounded as it is today. New cost is bounded output bytes and cells instead of N×500 regardless of the source budget.

**Regression:** Feed the pure shaping helper 100k tiny two-field documents whose field names rotate across 499 names; verify the returned serialized result and allocated cell count remain within configured budgets, `truncated_reason` is `bytes`, and early retained rows preserve values. Include a late-appearing field to ensure widening the union cannot retrospectively exceed the budget. A small allocation/serialization budget test can cover this without an external Mongo server; subsequently sample daemon and webview RAM on the same fixture.

### [MAJOR] P2-PERF-02 — A later SQL batch statement drains the earlier capped SELECT in full — `crates/otto-dbviewer/src/drivers/mysql.rs:2054`

**What:** Multi-statement execution bypasses server-side row-limit injection, stops reading each SELECT after the display cap, then executes the next statement on the same connection. Marking the connection `close_on_drop` does not close it before that next statement. SQLx therefore consumes the unread result before issuing the next query. A second small statement turns an otherwise bounded table preview into a full transfer of the first table.

**Cost:** Let R be rows from the first SELECT, K the display cap (default 1,000), and B average row bytes. For `SELECT * FROM large_table; SELECT 1`, useful displayed data is O(K×B), but transferred/drained data is O(R×B). At R=1M and B=200 bytes this is about 200 MB of unnecessary database traffic; 10M rows is about 2 GB. It delays the entire batch and occupies one of the six MySQL pooled connections until draining finishes. The same structural issue is present in the PostgreSQL batch path. This is a normal “run batch” action; input row count comes from the user's table, not the editor response limit.

**Evidence: Confirmed by call and dependency trace.** MySQL branches to `run_batch` before single-statement limit injection (`mysql.rs:728`, `:737`). The batch passes the original statement and `server_bounded=false` (`:2051`, `:2054`), sets close-on-drop for unread rows (`:2057`), and continues the loop. The reader stops at K+1 (`:2151`). Locked dependency version is sqlx-mysql 0.9.0 (`Cargo.lock:6106`); its installed `src/connection/executor.rs:112` calls `wait_until_ready` before executing, and `src/connection/stream.rs:68` receives packets until the pending result EOF. PostgreSQL has the equivalent intentional “later statement drains them” path (`crates/otto-dbviewer/src/drivers/postgres.rs:1924`, `:1927`). No database was contacted for this trace.

**Fix:** Apply the existing conservative row-limit injector to each eligible SELECT within a batch, passing the resulting bounded flag into `exec_read_conn`; pager availability can remain a separate UI decision. Plain preview SELECTs then send at most K+1 rows, so the two-statement scenario goes from R rows to K+1. For statements the injector cannot safely rewrite, define an explicit capped-batch policy that preserves session semantics and clearly reports whether later statements ran; do not silently open another connection and lose transaction/session state. The immediate safe fix should cover ordinary injectable SELECTs in both SQL drivers.

**Regression:** Against an isolated database, run a two-SELECT batch whose first table is much larger than K; assert the first server statement is bounded and rows/bytes read do not grow with R, the second result appears, and a session-dependent batch still uses the same backend connection. Include SELECT followed by a write to prevent a performance fix from silently changing later execution semantics.

### [MAJOR] P2-PERF-03 — Opening schema version history serially downloads every full version — `crates/otto-brokers/src/schema_registry.rs:329`

**What:** Each subject selection lists version numbers and then awaits a separate full-schema HTTP fetch for every version before returning anything. There is no history cache or page limit. The subject-list path already has eight-way concurrency and a TTL, but those safeguards do not apply to version history.

**Cost:** V is the number of registered versions of the selected schema, controlled by the remote registry and unbounded here. One click costs 1+V serial HTTP round trips and O(V×S) retained schema bytes, where S is average schema size. With 100 versions and an assumed 100 ms RTT, network latency alone is approximately 10.1 seconds; 500 versions is 50.1 seconds. Selecting another subject and returning repeats the work. The initial comparison uses only the newest two versions, so almost all bodies are eagerly loaded without being viewed.

**Evidence: Confirmed by hand trace.** The registry response supplies the entire version list (`schema_registry.rs:317`); the serial loop awaits both HTTP response and JSON body (`:329`, `:331`, `:337`), retaining each schema (`:342`). `SchemaVersionsPanel.svelte:34` reloads on subject changes, and defaults A/B to the newest two only after the whole response arrives (`ui/src/modules/brokers/SchemaVersionsPanel.svelte:49`, `:54`). A single-version detail method already exists (`schema_registry.rs:351`). The nearby cached/concurrent implementation is explicitly for `subjects`, not history (`:239`, `:297`).

**Fix:** Return version identifiers first and lazily fetch the two selected schema bodies through the existing detail capability. Cache immutable `(subject, version)` details with a byte bound; refresh the version-number list separately. Initial body fetches become two rather than V, with O(S) body retention for the active comparison. If the current contract must be retained temporarily, use bounded concurrency plus cancellation and a cache; that reduces latency but retains the eager body cost, so it is an interim fix.

**Regression:** A fake registry with 100 versions should observe one version-list request and at most two body requests when opening the comparison, no refetch for a previously loaded immutable version, and bounded concurrent requests during rapid subject switching. Verify version selection and diffs remain correct.
