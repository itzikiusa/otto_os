## Ranked findings

### [MAJOR] P5-01 — Assistant incremental indexing still clones the complete transcript — `crates/otto-server/src/assistant/threads.rs:756`

**What:** Every changed indexing tick calls `folder.snapshot()` and only then selects the final 30 turns. `Fold::snapshot` implements this as `self.clone().finish(record_count)` (`crates/otto-transcript/src/fold.rs:549`): old turns, tool blocks, indices and artifacts are copied even when only one new reply matters. Incremental file reading does not remove this full-history allocation. The 2 MiB transcript page budget is applied by paging; this caller never pages.

**Reachability:** Sending an Assistant message starts `drive_turn`; its indexing timer fires every 15 seconds while the CLI remains active (`crates/otto-server/src/assistant/threads.rs:373`, `:385`). `ReplyIndex::replies` skips an unchanged file, but any append reaches the snapshot (`:738`–`:756`). The fold spans the resumed session's lifetime. After snapshotting, `reply_texts` selects only the last 30 turns (`:786`).

**Cost:** Let B be retained folded history bytes, N its turn count, D the changed reply bytes, and A the number of active Assistant turns. A changed tick allocates/copies O(B), rather than only D, and keeps both the original and cloned fold alive. At a hypothetical 100 MiB folded history and uninterrupted changes, one active thread copies at least approximately 400 MiB/minute solely for snapshots; four such active threads multiply that by four. A 10× older transcript makes each otherwise identical small update approximately 10× more expensive in copied bytes. Per-block clipping does not bound the number of blocks/turns. This is a hot repeated cost on tool-heavy, long-lived threads, not a startup-only clone.

**Evidence:** Confirmed by hand tracing the production caller and deep-clone implementation. No allocation benchmark was run in this partition. The first index also reads/parses the entire transcript once per user turn (`:770`–`:773`); that is a separate existing initialization cost and is not counted in the per-tick estimate.

**Fix and payoff:** Expose a finalized bounded tail accessor for the initial last-30 index and use changed turns for subsequent ticks. `Folder::record_count` / `turns_since` already provide the delta mechanism (`crates/otto-transcript/src/lib.rs:105`, `:130`); preserve its finalization behavior. Track the prior record cursor and reset it when the file is replaced or a Codex era changes. Filter/cap reply text before copying unrelated tool blocks. This reduces repeated payload copying from O(B) to O(D); the current `turns_since` still scans N turn descriptors, which is cheaper but should not be advertised as a fully O(D) algorithm. It also avoids up to 30 unchanged `upsert_indexed_turn` SELECTs per changed tick (`threads.rs:691`, `crates/otto-state/src/assistant.rs:539`).

**Regression checks:** Large preseeded Claude and Codex transcripts followed by one appended assistant reply; unchanged polls; a growing last reply; tool-only append; partial JSONL line; replacement/truncation and Codex era reset. Assert identical indexed text/model/source refs and unchanged-turn DB-call counts; measure allocations versus history size with appended data held constant. Keep the initial last-30 backfill semantics.

### [MAJOR] P5-02 — Every visited Assistant thread stays cached and is refetched on reconnect — `ui/src/lib/stores/assistant.svelte.ts:273`

**What:** The singleton Assistant store has no release/eviction path for `turns`. Opening a thread inserts its full turn page; leaving the view does not remove it. WebSocket recovery loops through every accumulated key and calls `loadTurns` without a concurrency cap, even for threads that are no longer visible. Live events continue appending turns to those formerly visited threads, so the initial page size is not a lifetime bound.

**Reachability:** `ChatView` loads on mount but has no corresponding Assistant-store release (`ui/src/modules/assistant/ChatView.svelte:38`). `loadTurns` inserts the result (`ui/src/lib/stores/assistant.svelte.ts:133`); `setTurns` only adds/replaces keys (`:398`). `appendTurn` treats existence in the map as “open” and grows the array (`:389`). The global event reconnect path invokes `assistant.resync()` (`ui/src/lib/events.svelte.ts:546`), which eagerly queues all those loads (`assistant.svelte.ts:268`). The API's actual default page is **200** turns (`ui/src/lib/api/assistant.ts:36`), with a backend hard limit of 500 per request; that request limit does not bound cached thread count or live appends.

**Cost:** Let V be distinct threads visited since the webview started, P=200 initial turns per thread, and S average serialized turn bytes. Retained payload starts at O(V×P×S), then grows with live events. A reconnect schedules V requests returning up to V×P rows, plus the fixed global refreshes; request tickets reject stale responses but do not cancel the work. With V=100 and S=4 KiB, that is roughly 78 MiB of text/JSON payload and 20,000 rows per reconnect, before object overhead. Browser socket limits queue excess work rather than bound the overall batch, delaying the visible thread among background history reloads. Even V=20 produces 20 independent obsolete-view loads.

**Evidence:** Confirmed via all writes to the `turns` map and the production reconnect caller. No runtime heap or network capture was performed here. Ordinary short use with one or two threads will not exhibit the large-input cost.

**Fix and payoff:** Give Assistant thread data the same acquire/release lifecycle already used for transcript views. Refresh only actively acquired threads after reconnect; mark inactive entries stale and reload on their next acquisition. Bound inactive entries by an LRU/count or byte budget and stop appending to evicted entries. Bound any remaining refresh concurrency and abort obsolete requests. Preserve pending local sends independently of cache eviction. Reconnect turn fetches become O(active views), normally one, instead of O(V); retained inactive history becomes explicitly bounded.

**Regression checks:** Visit 100 threads, leave one visible, then reconnect: assert one active turn refresh rather than 100, a bounded inactive cache and no lost local pending turn. Switch back to an evicted thread and verify reload. Deliver a late fetch response and live events after release; ensure neither resurrects evicted heavy state. Run repeated visit/reconnect cycles and inspect heap growth and request counts.

### [MAJOR] P5-03 — Insights completion polling rereads every archived report — `crates/otto-server/src/insights.rs:331`

**What:** Every reports request enumerates all period artifacts, reads every summary in full before clipping to 80 lines, stats all three possible artifacts for each period, sorts all reports and returns every summary. During “Run now”, the UI repeats this whole archive query every three seconds just to see whether one requested report changed. Moving the scan to `spawn_blocking` protects Tokio workers but leaves its disk, serialization and transfer cost intact.

**Reachability:** `InsightsPage` starts the polling loop from the returned run ID and fetches the complete list at `ui/src/modules/insights/InsightsPage.svelte:466`; interval is 3,000 ms (`:489`), capped at 100 polls (`:411`). The route invokes `list_reports` without cache or a specific-period filter (`crates/otto-server/src/insights.rs:689`). The reader loops over every period (`:324`), performs a summary read (`:331`) and three artifact metadata lookups (`:335`). Home also calls the same complete-list API before selecting only the newest report per kind (`ui/src/modules/home/boxes/InsightsBox.svelte:32`, `:64`).

**Cost:** Let R be accumulated reports, F the average complete summary-file bytes and K≤100 completion polls. One request performs R summary reads, at least 3R artifact metadata lookups (plus existence checks and opens), O(R log R) sorting and O(R×summary-preview-size) serialization. A five-minute run at R=300 can trigger 30,000 summary reads and 90,000 explicit artifact stats; R=1,000 raises these to 100,000 and 300,000. Reads total K×R×F; the application still does this work when OS disk caches are warm. With daily/weekly/monthly reports, hundreds of periods are a normal archive rather than a contrived import. Hidden-window polling is already paused and identical-result rendering is avoided, but both checks leave visible polling's backend work unchanged.

**Evidence:** Confirmed request-to-filesystem trace and exact poll bound. These are counted operations, not measured latency or physical disk reads. A short archive or quickly finishing run has much smaller impact.

**Fix and payoff:** Poll a bounded status/revision for the requested run or report key, or consume the existing `insight_ready` event with a bounded status fallback. Reload archive metadata once after completion. Add a metadata-only paged report list and fetch a selected report's summary separately; provide a newest-per-kind projection for Home. Cache unchanged report metadata/previews by path + mtime, invalidating completed reports and tolerating external changes. Active-run detection goes from O(K×R) file work to O(K) bounded status checks plus one archive update; Home no longer transfers all archived summaries. A fixed TTL cache alone only reduces a constant factor and should not be represented as the complete fix.

**Regression checks:** Seed 300 and 1,000 report triples, poll one unfinished run, and count reads/stats and response bytes. Keep the counts per status poll independent of R. Verify re-running an existing period changes its revision, summaries written before HTML are handled, completed events missed across reconnect recover, and manual/external report edits become visible.

## Bounds verified and limits

- AWS CloudWatch log pages default to 200 with a 1,000-item cap; Insights queries cap result count, group count and time range (`crates/otto-aws/src/logs.rs:17`). AWS CLI has daemon-wide child permits with interactive capacity reserved (`crates/otto-aws/src/cli.rs:37`). Metrics queries batch series and use expiring cached answers; no per-series subprocess finding was asserted.
- Home's common polling helper uses a non-overlapping visibility-aware chain and freshness reuse (`ui/src/modules/home/boxes/poll.ts:16`). The Insights archive problem above concerns work inside each permitted refresh.
- History indexing peeks bounded head/tail data, skips matching mtime/size, runs one scan at a time and yields between changed files (`crates/otto-server/src/history_index.rs:167`). Its startup file enumeration was not promoted to a hot-path finding.
- Proof list responses fetch metadata for the requested page in a batch, and previews are clipped in SQL (`crates/otto-server/src/routes/proof.rs:139`, `:198`). Legacy unbounded listing exists, but this pass did not prove an active high-volume caller and does not duplicate a generic missing-pagination complaint.
- Live room registry caps rooms at 32 and admitted members at four, with expiry (`crates/otto-server/src/rooms/registry.rs:183`, `:273`). Quadratic audio routing over four members is not a scaling finding. Recap storage/processing has archive and summary-input limits; lifetime archive indexing deserves later workload measurement but was not asserted as a blocker here.
- Settings log display retains at most 5,000 lines and follows incremental offsets; whole-history log rendering was already addressed (`ui/src/modules/settings/Logs.svelte:23`).
