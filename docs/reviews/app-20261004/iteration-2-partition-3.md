## R2-P3-03 — Major: The workspace-loading effect now tracks story selection and immediately clears every opened story

**Locations:** `ui/src/modules/product/ProductPage.svelte:303`; `ui/src/lib/stores/product.svelte.ts:143`, `:240`, `:262`, `:896`.

**Confirmed by hand trace, consistent with root's rendered failure:** The effect intended to reload only on `ws.currentId` calls `product.teardown()` and `loadStories()` synchronously. The newly added `loadStories()` ownership capture calls `owner('loadStories', true)` before its first await. `owner()` unconditionally reads reactive `this.selectedId`, although a workspace-only request does not use that captured story. Svelte therefore adds `selectedId` to the page effect's dependencies. Clicking story A sets that state, reruns the effect, and invokes teardown again. The new teardown clears the selected detail and resets `selectedId` to null; it also advances the generation, correctly rejecting A's pending detail response afterward. The view returns to its collection summary instead of opening A. This affects normal story selection, not just cancellation or a rare race.

**Fix:** Explicitly isolate the workspace effect: track `ws.currentId`, then run its teardown/loading side effects inside `untrack`. Also avoid reading selection state in `owner()` for workspace-only operations. Preserve generation fencing for actual story-owned requests.

**Verification:** Render Product with at least two real/stubbed stories, select each and assert the chosen detail remains mounted without another workspace list request/teardown. Then change workspace and verify exactly the intended reset/reload. Only after this passes can the canceled-tab-focus scenario reach its relevant controls. Root's `/tmp/otto-review-product-focus-red.log` fails in `openOverview` before the focus assertion, so it is evidence of a blocked opening flow, not behavioral-red evidence for R2-P3-01. `ui/unit/sourceHarness.ts` replaces `$effect` with a no-op and runes with identities; the passing ownership tests cannot detect this dependency subscription.

## R2-P3-01 — Minor: Canceling guarded Product tab navigation leaves focus on an inactive tab

**Locations:** `ui/src/modules/product/ProductPage.svelte:610`, `:780`, `:799`; `ui/src/lib/tabKeys.ts:45`, `:53`; `ui/src/lib/stores/product.svelte.ts:229`; `ui/src/lib/dialogFocus.ts:31`.

**Confirmed by hand trace:** With an unsaved draft and Overview selected, focus its active group/sub-tab and press ArrowRight. The shared handler focuses the next tab *before* calling its click handler. Product's handler now awaits `mayLeaveDraft()`, which opens the discard confirmation. The dialog records the already-focused destination as its return target. Choose Keep editing: `changeTab()` returns with the old tab selected, and dialog teardown restores focus to the attempted destination even though it remains `aria-selected=false` and `tabindex=-1`. The next arrow uses the focused destination's index, skipping the immediate neighbor of the still-active tab. The same mismatch occurs for Stories → Learnings cancellation. Draft contents are preserved; the remaining defect is focus/selection consistency.

**Fix:** Make these guarded Product transitions restore focus to the actual selected tab after their asynchronous decision and modal focus restoration settle; successful transitions should focus the newly selected tab. Keep the shared synchronous tab helper's behavior for unguarded consumers, or introduce an explicit awaitable activation contract rather than assuming `.click()` can be awaited.

**Verification:** A rendered test must dirty a draft, use keyboard navigation on each of the three tablists, cancel, and assert both selection and `document.activeElement` remain on the active tab. Repeat the arrow to verify the same neighboring destination is proposed, then allow navigation and verify destination focus. Store-only tests do not exercise the modal/focus integration. Root's first rendered attempt was blocked earlier by R2-P3-03; this focus finding remains source-traced, to be executed after opening is repaired.

## R2-P3-02 — Minor: A backlink refresh removes contexts for already-expanded rows and offers no way to load them again

**Locations:** `ui/src/modules/vault/vault.svelte.ts:372`, `:790`, `:802`; `ui/src/modules/vault/RightPanel.svelte:17`, `:23`, `:67`; `crates/otto-vault/src/engine.rs:1787`.

**Confirmed by hand trace:** Open a note with 126 backlinks. Initial load hydrates 100 contexts; Show more fetches offset 100, hydrates the remaining 26, and increases `shownBacklinks` to 200, hiding Show more. Let another vault edit advance the generation. The ordinary status refresh calls `reloadBacklinks()`, which requests the default first window and replaces the entire list. The server explicitly returns empty contexts outside that window, even if they exist in its cache. RightPanel resets its visible limit only when `notePath` changes, so all 126 rows remain displayed but rows 101–126 lose their contexts. Since `126 > 200` is false, no Show more control remains to retrieve them. A larger list similarly skips the newly blank visible window when requesting the next offset.

**Fix:** Keep the visible-range and hydration state consistent across refresh. Rehydrate the currently visible windows with the existing bounded requests, or explicitly reset the visible limit when the backlink generation/list is refreshed so the missing window can be requested again. Do not blindly retain old snippets across changed source hashes. Preserve the per-request maximum of 100 source reads.

**Verification:** With 126 nonempty-context backlinks, expand once, trigger the normal external-generation refresh, and assert either all visible contexts are rehydrated or the view resets to 100 with a working Show more. Repeat with more than 200 rows, and with a backlink source edited between reads. The Rust 126-source fixture verifies server window bounds but not this UI refresh sequence.
