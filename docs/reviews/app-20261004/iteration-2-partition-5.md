## Remaining finding

### R2-5-01 — major — Explicitly resuming a task in a later turn keeps its obsolete execution binding

**Original mapping:** C5-02.

**Location:** `crates/otto-server/src/assistant/tasks.rs:248`; cancellation sink `crates/otto-server/src/assistant/threads.rs:122`; state settlement `crates/otto-server/src/assistant/tasks.rs:739`.

**Intended:** The running task that the agent explicitly resumes should control that current operation when the user presses Stop. An unrelated replacement turn must remain protected from a stale task. Both guarantees are needed; merely retaining the first execution ID satisfies the latter but breaks the former.

**Confirmed source trace:**

1. During thread turn E1, `assistant_create_task` stores `thread_execution_id=E1` (`tasks.rs:185`). Leave the task nonterminal when E1 ends, for example while it is waiting on a question.
2. The user sends a normal follow-up in that same thread; the new driver claims E2. The agent resumes the same task via the supported `assistant_update_task(task_id, state="running")` tool (`crates/otto-server/src/assistant/tools.rs:177`). This path is separate from the card's approve/handback path, which does explicitly rebind.
3. `agent_update` permits the state change and clears the question, but only binds an execution when the existing field is **None** (`tasks.rs:248`). The task is shown running under E2 while its stored ID remains E1.
4. Stop enters `stop_task_execution`, passes the stored E1 to `threads::stop_execution` (`tasks.rs:829`), and finds that the active ID is E2. The helper correctly refuses to signal E2 but returns **Ok** for the stale binding (`threads.rs:122`). `act` then commits `cancelled` (`tasks.rs:739`) while E2 continues the work the agent has just associated with that task. Takeover of that task instead returns 409.

**Fix direction:** Carry the calling thread/session identity from the already-resolved tool context into the explicit task-update operation. When that operation accepts a transition/update to running from the task's current owning thread execution, atomically rebind to that verified execution. Otherwise reject the stale update without advertising resumed execution. Preserve `stop_execution`'s existing protection against a stale task that has **not** been explicitly resumed; do not change it to stop whichever turn happens to be current.

**Regression:** Create T in E1; finish E1; claim E2; update T to running through the production tool/update path; cancel T and verify E2 receives the stop signal. Also retain the existing inverse test: without an explicit resume, cancelling old T must not signal unrelated E2. Include a different calling thread/session so it cannot seize another task's current execution. The present `stopping_an_old_task_never_signals_a_replacement_turn` test exercises only the inverse case and would pass while this resumed-task case remains broken.

## Corrected during this recheck: Insights status route policy

The parent identified that the new `/insights/report-status` route was absent from the feature-policy table. Independently traced: it fell through `policy_for` to `Deny` (`policy.rs:1416`), and `feature_guard.rs:211` evaluates Deny before the root bypass inside Require. Therefore even root received 403. Completion polling caught the error and kept retrying until timeout; missing-page deep-link hydration also failed. Direct filesystem/helper tests could not catch this integration defect.

The parent's current patch adds the exact route to `Require(Insights, View)` at `policy.rs:936` and an explicit assertion near `:2421`. It also changes the read-route Auth labels in `docs/contracts/api.md:2644` to Insights:View, matching the existing policy and new route; PUT/POST retain their actual handler-level root restrictions. This correction is **verified in source, pending the central final test gate**. It is not counted as an outstanding defect in this report.
